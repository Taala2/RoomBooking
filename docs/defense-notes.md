# Темы для защиты и собеседования

Короткие ответы на вопросы, которые чаще всего задают по этому проекту, со ссылками на код и тесты.

## 1. Как гарантируется, что комнату нельзя забронировать дважды?

**Проблема.** Сервис сначала ищет пересечение (`get_conflict_booking`), потом вставляет бронь. Между этими шагами другой запрос может сделать то же самое — оба увидят «свободно», и обе брони сохранятся. Это классическая гонка check-then-act.

**Почему не `SELECT ... FOR UPDATE` по броням.** Он блокирует только найденные строки. Когда пересечений нет, блокировать нечего — новую строку (фантом) это не защищает.

**Почему не блокировка строки комнаты или advisory lock.** Работает, но гарантия держится на дисциплине: любой новый код, который пишет брони без этой блокировки (админка, скрипт, ручной `INSERT`), её обходит.

**Решение — EXCLUDE-ограничение PostgreSQL** (`alembic/versions/0003_bookings_no_overlap.py`):

```sql
EXCLUDE USING gist (room_id WITH =, tstzrange(start_time, end_time, '[)') WITH &&)
WHERE (status = 'ACTIVE')
```

- правило проверяет сама база, обойти его нельзя;
- `btree_gist` нужен, чтобы в одном GiST-индексе сравнивать `room_id` через `=`;
- `[)` — конец не входит в интервал, поэтому брони «встык» (10–11 и 11–12) разрешены;
- отменённые брони не участвуют (`WHERE status = 'ACTIVE'`; SQLAlchemy хранит enum по имени, отсюда `'ACTIVE'`, а не `'active'`).

**Две ошибки, которые означают «занято»** (`save_without_overlap` в `bookings/bookings_services.py`): `23P01` — пересечение с уже сохранённой бронью; `40P01` — две пересекающиеся вставки ждали друг друга, и PostgreSQL прервал одну как deadlock. Обе превращаются в `409`. Deadlock всплыл только на тесте гонки — примерно в половине прогонов.

**Как доказано.** `tests/concurrency/test_booking_race.py`: два потока, у каждого своя сессия; `threading.Barrier` заставляет оба запроса пройти проверку до вставки, поэтому гонка воспроизводится стабильно. До ограничения тест падал (`['created', 'created']`), после — ровно одна бронь и один конфликт, 20 прогонов подряд.

## 2. Как устроена работа со временем?

- В базе `timestamptz`, в API принимается только время с часовым поясом (`AwareDatetime`, иначе `422`), внутри всё приводится к UTC.
- Фронтенд показывает время в часовом поясе пользователя и отправляет `toISOString()` (UTC).
- Старые данные были в `timestamp without time zone` и сохранялись в часовом поясе сервера (`Asia/Almaty`). Миграция `0002` переводит их через `AT TIME ZONE current_setting('TimeZone')`, а не через `'UTC'` — иначе все брони сдвинулись бы на 5 часов. Проверено предпросмотром до применения.

## 3. Как подключали Alembic к уже существующей базе?

- Ревизия `0001` написана вручную и повторяет **реальную** схему базы (а не модели): в базе `role` был `VARCHAR`, `email` допускал `NULL`. Совпадение проверено сравнением схем на временной базе.
- Существующая база помечена `alembic stamp 0001` — данные не тронуты.
- `0002` приводит базу к моделям; `alembic check` после неё — без расхождений.

## 4. Архитектура

- Модули `users`, `rooms`, `bookings`, в каждом роутер → сервис → репозиторий.
- Сервисы бросают доменные исключения (`BookingConflictError`, …) и не знают про HTTP; `core/handlers.py` превращает их в коды ответов.
- **Компромисс:** `commit()` внутри репозиториев — одна запись = одна транзакция. Операций из нескольких записей нет, поэтому этого достаточно; ошибки при коммите ловятся в сервисе вокруг вызова репозитория.
- Новых слоёв не добавлялось: доработки — точечные изменения в существующих файлах.

## 5. Безопасность

- Пароли — bcrypt; длина ограничена **72 байтами** (лимит bcrypt), иначе было бы `500` — найдено на код-ревью.
- Неизвестный логин и неверный пароль дают одинаковый `401`, и время ответа тоже одинаковое (для неизвестного логина пароль сверяется с фиктивным хешем).
- JWT обязан содержать `exp` и `sub`; любая ошибка токена — `401`, а не `500`.
- `SECRET_KEY` берётся из `.env`, не короче 32 символов; заглушка из `.env.example` отклоняется при старте.
- Права проверяет backend: удаление комнаты только админом (раньше путь был `/roomsdelete/...` без проверки прав), админ не может сменить роль себе.
- CORS — явный список адресов, без cookies; токен в заголовке. Хранение токена в `localStorage` — осознанный компромисс (риск XSS), описан в README фронтенда.

## 6. Тестирование

- PostgreSQL обязателен: SQLite не поддерживает EXCLUDE-ограничения. Тестовая база `<имя>_test` пересоздаётся и мигрирует теми же миграциями; на имя без `_test` тесты не запустятся.
- Изоляция: каждый тест в транзакции, которая откатывается (`join_transaction_mode="create_savepoint"`), — `commit()` в репозиториях не мешает. Тесты гонок используют настоящие коммиты и очищают таблицы.
- Каждый исправленный баг сначала воспроизводился падающим тестом (`xfail(strict=True)` до исправления, затем обычный тест).
- 102 теста, покрытие кода приложения ≈ 98%, CI на GitHub Actions с PostgreSQL 17; тот же сценарий проверяется локально на Linux в Docker.

## Быстрая демонстрация

```bash
docker compose up --build -d
docker compose exec api python -m scripts.seed --login admin --email admin@example.com
```

Интерфейс — http://localhost:5173, Swagger — http://localhost:8000/docs. Сценарий: регистрация → бронь → попытка забронировать пересекающееся время (`409`) → перенос → отмена → вход админом → управление комнатами.
